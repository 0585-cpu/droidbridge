# 지속 부하와 연결 복구 개선 — 2026-10-15

삼성 실행 제한이 시작된 뒤 USB 재전송이 늘고, Mac의 상태 확인 재시도가 끝나 수동 재연결이 필요했던 경로를 보완했다. 기존 기능을 유지하면서 반복 작업을 줄이고, 휴대폰이 다시 응답하면 인증을 확인한 뒤 통신 엔진을 새로 시작한다.

| 변경 | 기대 효과와 범위 |
| --- | --- |
| Android 셀룰러 속성을 네트워크 콜백에서 보관 | 패킷 처리 중 반복되던 동기 `getLinkProperties` 호출 제거. IPv6·NAT64·DNS는 현재 네트워크의 소유된 스냅샷에서 읽는다. |
| 초기 IPv6 준비 상태를 ICMP 기능 캐시에 반영 | 첫 속성 콜백 이전 조회로 IPv6 기능이 계속 누락되는 경우 방지. 기존 IPv4 연결은 유지한다. |
| 속도 제한이 없는 프로필의 빠른 처리 경로 | 패킷마다 공용 속도 제한 잠금과 버킷 처리를 거치지 않는다. 취소 확인과 실제 제한 프로필은 유지한다. |
| Android·Mac USB 재전송 간격 조절 | 반복 손실 시 500 → 1,000 → 2,000ms로 간격을 늘려 중복 쓰기·해시 작업을 줄인다. 실제 ACK 진전은 이후 간격을 초기화한다. |
| Mac의 장시간 자동 복구 | 짧은 재시도 이후에도 5 → 10 → 20 → 최대 30초 간격으로 인증된 상태 응답을 확인한다. 응답이 돌아오면 새 통신 엔진으로 복구한다. |

USB의 32개 전송 창, 10초 무진전 종료 기한, 데이터 무결성 검사와 순서는 그대로 유지했다. 반복 손실 이후의 재전송은 최대 2초 늦어질 수 있다. Mac의 기존 250ms USB 작업 확인 주기를 모두 없앤 변경은 아니다.

인증 실패나 잘못된 프로토콜 응답은 자동 복구를 중단한다. 실제 전송 계층의 EOF는 다시 인증을 시도할 수 있도록 구분했다. 연결 해제 요청이나 이전 작업의 늦은 응답이 새 연결을 시작하거나 종료하지 못하도록 검사했다. 휴대폰이 제한되는 동안 종료된 Parsec 세션 자체가 보존되는 것은 아니다.

- Android 단위 검사 268개 통과. Lint 오류 0개, 경고 19개. APK·검사 APK 빌드 및 서명 확인.
- Swift 공용 검사 317개, USB 전체 검사와 Mac 도우미 전체 검사 통과.
- Mac Release 앱·도우미 서명 확인. 설치된 앱·도우미·APK 해시가 준비한 빌드와 일치.
- 휴대폰 실제 셀룰러 TCP·DNS 및 UDP 검사 9개 통과. USB 경로로 HTTPS 204 확인.

15:42:32–15:52:32 KST의 10분 동시 사용 관찰은 **연결 유지 검증 실패**로 기록했다.

- 40개 상태 표본 모두 USB 경로였다. 34개에서 앱이 `/abnormal` 실행 그룹에 있었고, 25개에서 `FROZEN` 상태를 직접 확인했다. 표본 개수는 독립 장애 횟수가 아니다.
- Mac HEALTH 복구 기록은 8회, 통신 엔진 차단은 5회였다. 차단 뒤에도 재시도를 계속하고 인증된 응답으로 자동 복구한 새 동작을 확인했다. USB 장치 세션 자체의 종료 기록은 없었다.
- 주 HTTPS 검사 60개 중 13개가 실패했다. 마지막 별도 5개 검사에서는 3개 성공·2개 실패였다. DNS 시간 초과 등 같은 제한 구간에서 발생한 실패들을 별개의 장애로 세지 않는다.
- 15:51:15에 Parsec이 `-12007` 상태로 연결을 종료했다. 이 코드 자체의 의미를 이번 조사에서 단정하지 않는다.
- 앱 CPU 평균은 한 코어 기준 16.9%였지만, 실행 제한과 정지 구간을 포함하고 트래픽도 이전과 동일하지 않다. 이전 26.48%와 비교해 최적화 효과라고 해석할 수 없다.

관찰기에서 curl의 HTTP 코드 `000`이 올바른 JSON 숫자가 아니어서 실패 표본을 누락하는 문제도 바로잡았다. 원본을 보존했고, 수정된 요약은 실제 60개 표본과 오류 출력을 함께 반영한다.

검증 후 USB를 수동 종료하고 대체 Wi-Fi(`en0`)로 복원했다. 복원 후 HTTPS 204 응답을 확인했다. 새 앱·APK·도우미는 설치된 상태로 유지했다.

따라서 이번 변경은 반복 작업 완화와 자동 복구를 제공하지만, 삼성 실행 제한과 Parsec 끊김을 해결한 상태는 아니다. 제한의 정확한 발동 조건과 전체 CPU의 함수별 비중은 아직 확정되지 않았다. 다음 단계는 동일 트래픽·열 상태에서의 부하 비교 및 열 상태에 맞춘 트래픽 조절 설계다. 삼성 열 보호와 전원 정책은 변경하지 않았다.
