# DBP/1 — DroidBridge Protocol, version 1

DBP/1 is the control protocol between the macOS Packet Tunnel (client) and the
Android relay (server) over an AOA multiplexed loopback TCP connection
(`127.0.0.1:27183`). This document preserves the original B1 TCP/DNS/HEALTH wire format.

The implemented UDP, CAPABILITIES, IPv6 and ICMP additions are defined in the
[extension contract](../docs/superpowers/specs/2026-09-23-droidbridge-implementation-contract.md)
and `protocol/test-vectors/dbp-extensions.json`. They retain the same 64-byte header,
HMAC and HELLO exchange. Query CAPABILITIES on a separate authenticated connection;
HEALTH is unchanged. EOF before an extension response from an authenticated old peer
means legacy TCP4-only; bad HMAC/nonces, truncated responses and timeouts fail closed.

Canonical test vectors: `protocol/test-vectors/dbp-v1.json`, generated by
`tools/generate_protocol_vectors.py`. Implementations in C, Kotlin and Swift
must match those vectors byte for byte.

## 1. Common header (64 bytes)

All integers are unsigned, network byte order (big-endian).

```text
Offset  Size  Field
0       4     Magic = "DBP1" (0x44 0x42 0x50 0x31)
4       1     Message type
5       1     Flags — MUST be 0 in DBP/1
6       2     Header length — MUST be 64
8       8     Client nonce
16      8     Server nonce — 0 in HELLO; otherwise the nonce from HELLO_OK
24      8     Unix time, seconds
32      32    HMAC-SHA256
64      N     Type-specific payload
```

Decoding rules:

- Fewer than 64 bytes available → `TRUNCATED`. Never read past the buffer.
- Magic mismatch → `MAGIC`.
- Header length ≠ 64 → `HEADER_LENGTH`. (The common header has no variable-length extensions.)
- Unknown message type → `MESSAGE_TYPE`. Non-zero flags → `FLAGS`.
- Any of the above is a protocol error; the receiver closes the connection.

## 2. Authentication

Every message carries `HMAC-SHA256(secret, header_with_zeroed_hmac || payload)`.
The secret is the 256-bit Pairing Secret. Verification uses a constant-time
comparison.

- `|receiver_time − unix_time| > 120 s` → reject (`AUTH_FAILED`).
- Client nonce is fresh per connection. The server keeps the most recent 1024
  client nonces for 5 minutes; a repeated nonce is a replay → reject.
- After `HELLO_OK`, the client copies the server nonce into every subsequent
  header on that connection. A mismatch → reject.

HMAC failure, timestamp skew and replay all produce `OPEN_ERROR AUTH_FAILED`
(or a silent close before `HELLO_OK`). The relay never distinguishes them to
the peer.

## 3. Message types

```text
0x01 HELLO            client → server   payload: none
0x02 HELLO_OK         server → client   payload: none (server nonce in header)
0x10 OPEN_TCP         client → server   payload: destination (§4)
0x11 OPEN_OK          server → client   payload: none; socket becomes raw stream
0x12 OPEN_ERROR       server → client   payload: error code u8 (§6)
0x20 DNS_QUERY        client → server   payload: len u16 | DNS wire packet
0x21 DNS_RESPONSE     server → client   payload: len u16 | DNS wire packet
0x30 HEALTH           client → server   payload: none
0x31 HEALTH_RESPONSE  server → client   payload: §5
```

## 4. OPEN_TCP payload

```text
1 byte   address type: 1 = IPv4, 3 = domain
2 bytes  destination port, 1…65535
1 byte   address/domain length
N bytes  address (exactly 4 for IPv4) or domain (1…253 bytes, ASCII/IDNA
         wire form, no trailing dot, no NUL terminator on the wire)
```

Rejections: unknown address type → `ADDRESS_TYPE`; port 0 → `PORT`; IPv4
length ≠ 4 or domain length 0 or > 253 → `DOMAIN_LENGTH`; payload shorter
than declared → `TRUNCATED`.

The server applies the destination policy (`protocol/test-vectors/destination-policy.json`)
to the IPv4 address, or to every address returned by cellular DNS for a domain,
and again to the address actually used for the connection.

## 5. HEALTH_RESPONSE payload (22…85 bytes)

```text
1 byte   status: 0 = NOT_READY, 1 = READY, 2 = CELLULAR_UNAVAILABLE
2 bytes  active sessions
2 bytes  maximum sessions (≤ 256)
8 bytes  uploaded bytes
8 bytes  downloaded bytes
1 byte   carrier-name length, 0…63
N bytes  carrier name, UTF-8
```

Reject if active > maximum, maximum > 256, the name is not valid UTF-8, or the
length byte disagrees with the remaining payload.

## 6. Error codes (OPEN_ERROR)

```text
1 AUTH_FAILED           4 CELLULAR_UNAVAILABLE   7 CONNECT_REFUSED
2 VERSION_UNSUPPORTED   5 DNS_FAILED             8 SESSION_LIMIT
3 POLICY_DENIED         6 CONNECT_TIMEOUT        9 INTERNAL_ERROR
```

Any other value is a protocol error.

## 7. DNS payload

`len` (u16) must equal the number of remaining payload bytes and be 12…4096.
The DNS packet is passed through unchanged; the relay preserves the
transaction ID.

## 8. Session flows

TCP flow — one DBP connection per flow:

```text
connect 127.0.0.1:27183
  → HELLO            ← HELLO_OK
  → OPEN_TCP         ← OPEN_OK | OPEN_ERROR (then close)
  ⇄ raw application bytes until either side closes
```

After `OPEN_OK` there is no further framing; no DBP control message may be
sent on that socket again.

DNS — one query per connection:

```text
connect → HELLO ← HELLO_OK → DNS_QUERY ← DNS_RESPONSE → close
```

Health: `connect → HELLO ← HELLO_OK → HEALTH ← HEALTH_RESPONSE → close`.

## 9. Limits

- Maximum payload the relay will read: 4098 bytes (DNS len + 4096).
- Default 128 concurrent TCP sessions, hard limit 256 → `SESSION_LIMIT`.
- Test fixture secret: `00…0001` (31 zero bytes then `0x01`). Never use it
  outside tests.

## 10. Privacy

Neither side logs payloads, DNS names, domains from `OPEN_TCP`, or the secret.
Diagnostics may record message type, error code, byte counts and timings only.

## UDP source associations (capability bit 10)

Peers advertising `UDP_ASSOCIATION = 1 << 10` accept authenticated message
`OPEN_UDP_ASSOCIATION (0x44)`. Its fixed four-byte payload contains family (4 or 6),
a reserved zero byte, and a big-endian uint16 idle timeout (30–300 seconds).
The reply is the existing `OPEN_UDP_OK` or `OPEN_UDP_ERROR`. The successful reply
retains its eight-byte layout and maximum datagram payload of 1472 bytes (IPv4 UDP at the 1500-byte tunnel MTU; IPv6 is held to 1452 by the MTU).
The host treats that maximum as the relay's limit: it never sends a larger datagram on the
stream, uses the smaller of the two limits, and refuses an advertised value below 512.
Without this capability the host retains the existing per-destination `OPEN_UDP`.

Each association stream owns one unconnected cellular UDP socket. The host groups
packet-engine flows by their original numeric source address, family and port,
allowing the same socket to contact multiple peers. IPv4 and IPv6 are separate.
The Android cellular network may still translate external ports per destination;
this extension does not promise endpoint-independent carrier NAT.

After OPEN, each datagram has a 28-byte header followed by its payload:

| Offset | Size | Value |
| --- | --- | --- |
| 0 | 2 | Payload length, big-endian, 0–1472 |
| 2 | 1 | Direction: 0 Mac to phone, 1 phone to Mac |
| 3 | 1 | Association family, 4 or 6 |
| 4 | 4 | Sequence, big-endian uint32 |
| 8 | 2 | Peer port, big-endian uint16, nonzero |
| 10 | 2 | Reserved, zero |
| 12 | 16 | Numeric peer address; IPv4 uses first four bytes and twelve zeros |

The receiver validates header bounds, padding, direction and family before
reading the bounded body. Zero-length packets remain distinct datagrams.
Android applies destination policy to every outbound peer and admits inbound
packets only from an endpoint previously sent to and still active within the idle interval.
Valid traffic in either direction refreshes that endpoint; unknown or oversized
inbound packets do not.
The peer set is limited to 256. The association uses the existing aggregate
traffic shaping and TTL/hop policy and bounded queues (64 datagrams, 256 KiB).
Oversized and unsolicited packets are dropped and counted. Stop, idle expiry,
stream EOF or cellular generation change closes the socket. Host flow retirement
discards that flow's unsent packets, and retiring the final flow closes the
association. Session ownership tokens fence delayed callbacks after replacement.
Canonical control fixtures and raw packet literals are in `test-vectors/dbp-extensions.json`.
